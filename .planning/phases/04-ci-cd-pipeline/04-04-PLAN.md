# Plan 04-04 — Execute rollback drill on prod VPS (live, supervised), update deploy.md §6.4 с results

<objective>
Live execution of CICD-04 drill scenario (user redline acceptance: "no-op rollback doesn't count"). Uses scaffolding от Plan 04-03b (Makefile rollback target + drill migrations 9990/9991 + drill_assert_schema.sh) + Plan 04-03a (backend-cd.yml publishes signed images on tag push).

**Drill sequence:**
1. Announce 10-min cutover window к user (no active mobile-client traffic recommended per RESEARCH Architectural Responsibility Map A3)
2. Tag `v1.0.0-rc.test-a` at current main HEAD (compose includes drill migration 9990 — adds users.metadata column); backend-cd.yml builds + signs + pushes 8 images
3. Deploy A к prod via `ansible-playbook -i inventory/prod --tags sport-stack site.yml`; verify migration 9990 applied via `drill_assert_schema.sh expect-present` (column present)
4. Commit drill migration 9991 (drops users.metadata) + tag `v1.0.0-rc.test-b`; CD re-builds + re-deploys; verify column DROPPED via `drill_assert_schema.sh expect-absent`
5. **THE DRILL:** `make rollback v=v1.0.0-rc.test-a` — git checkout test-a + migrate down 1 (re-adds column, undoes B) + ansible re-deploys A's binaries + smoke probe
6. Verify drill success via `drill_assert_schema.sh expect-present` (column re-present = A's schema restored)
7. Record timing в SUMMARY + extend `docs/RUNBOOKS/deploy.md §6.4` с drill procedure + results table
8. OPTIONAL: `make drill-clean` (delete drill tags from origin) — default = keep as historical record per user preference

Risk mitigation per RESEARCH Pitfall 5: drill migrations are backward-compatible NULLABLE-add/drop only; если drill aborts mid-way, prod stays serving valid data. Also: `pg_dump` taken before drill начинается (Task 1) — explicit safety net.

Purpose: deliver CICD-04 execution acceptance ("rollback drill validated с real DB migration в path").
Output: deploy.md §6.4 extended с drill results table; SUMMARY records all timing + outcomes; drill artifacts (tags + migrations) preserved or cleaned per user preference.

**Ansible re-deploy command:** `cd infra/ansible && ansible-playbook -i inventory/prod --tags sport-stack -e sport_stack_tag=<TAG> site.yml` (Phase 3 deploy.md §5.2 base form + `-e` extra-var per Plan 04-03a W4 fail-fast SPORT_STACK_TAG requirement).

**Migration container invocation (run-once):** Triggered automatically by sport-stack systemd umbrella on next deploy — `migrations` container runs `migrate up` (which is idempotent — applies pending migrations only). Drill-specific scenario:
- Tag test-a includes migration 9990 (ADD COLUMN) → ansible-playbook → migrations container applies 9990 → users.metadata appears
- Tag test-b includes migrations 9990 + 9991 → migration 9991 (DROP COLUMN) runs after 9990 → users.metadata disappears
- `make rollback v=v1.0.0-rc.test-a`:
  - git checkout test-a (working tree reverts к state where 9991 file doesn't exist)
  - `ssh deploy@... 'docker compose run --rm migrations down 1'` — runs 9991's down.sql (which re-adds the column) — undoes B's effect
  - ansible-playbook re-deploys A's binaries → migration container sees current state matches what's in 9990 → no-op
  - Final state: users.metadata column present (A's schema restored = drill PASS)

**Schema assertion command:** `bash services/backend/scripts/drill_assert_schema.sh {expect-present|expect-absent}` per Plan 04-03b Task 3.
