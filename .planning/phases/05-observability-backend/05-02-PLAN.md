<objective>
**USER-ACTION mini-plan** — Plan 05-02 v2 after ADR-0010 reshape (Sentry self-hosted → SaaS).

This plan is **majority human action in the sentry.io UI** + a small SOPS-write step. Original Plan 05-02 (`getsentry/self-hosted install.sh` via Ansible + sentry-cli project creation + custom Go alerter service for Telegram fan-in) is scrapped in favor of using sentry.io's SaaS infrastructure + native Telegram integration.

**Why this is short:** the heavy lifting (Sentry SDK init, OTel exporter, slog handler, PII scrub, dashboards, alerts) all happens in OTHER plans (05-03 ✅ already shipped, 05-04, 05-05, 05-06, 05-07). This plan is the SOPS substrate every other plan reads from.

**Why autonomous=false:** the user MUST create the sentry.io org + 4 projects in the SaaS UI (no API automation without an existing API token, which requires logging in first). User also generates BotFather + Telegram chat manually + configures Sentry's UI integration manually. Orchestrator's role is to (a) write the RUNBOOK + (b) verify SOPS slot once user pastes values.

**Purpose:** Two of Phase 5's eight ROADMAP success criteria depend on this plan landing:
- **Criterion 1** "Sentry self-hosted on separate VPS with own ACME cert" → reframed by ADR-0010 to "Sentry crash reporting available at the operator level" (sentry.io independent of both VPSes)
- **Criterion 2** "4 Sentry projects scoped (env × platform)" — preserved verbatim; sentry.io projects fulfill this
- **Criterion 8** (partial) "Alert rules wired to Telegram bot" — Sentry-side criticals route via sentry.io native Telegram integration; Grafana-side warnings route via Plan 05-07 D-26 codified rules.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User scratchpad → SOPS encrypted file | DSNs + bcrypt hash + Telegram token transit from sentry.io UI / BotFather / local terminal → SOPS-encrypted .yaml; never via chat (Phase 2 SEC-02 discipline preserved) |
| sentry.io SaaS → repo | DSN is a shared secret — anyone with the DSN can submit events; rotation playbook documented in §2 |
| Telegram bot token → repo | Bot token grants full bot control; rotation via BotFather `/token` documented in §3 |
| Sentry alert webhook → @running-ecosystem-alerts | sentry.io is trusted alert source; chat membership scoped to 2 devs |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01-I | Info disclosure | DSN leaked via chat / commit | mitigate | Phase 2 pre-commit gitleaks catches `sentry\.io.*/[0-9]+` DSN pattern; SOPS makes values safe at rest; user instructed NOT to paste DSN in chat |
| T-05-02-02-I | Info disclosure | Telegram bot token leaked | mitigate | Same as DSN — pre-commit + SOPS + user discipline; rotation playbook in RUNBOOK §3 |
| T-05-02-03-S | Spoofing | Forged Sentry event via leaked DSN | accept | DSN is single-tenant per project; abuse = quota exhaustion not data tampering; mitigated by sentry.io rate-limits + quota alerts (R-01) |
| T-05-02-04-E | Elevation of privilege | sentry.io org admin compromise | accept | 2-dev team; sentry.io 2FA enforced; user enables 2FA in Task 1 |
| T-05-02-05-T | Tampering | sentry.io stored events tampered | accept | sentry.io trusted operator; out of v1.0 threat model |
| T-05-02-06-D | DoS | Telegram bot spammed via leaked token | mitigate | Bot single-purpose (alerts only); compromise visible immediately; rotation <5 min via BotFather |

</threat_model>
