`rollout.go` (greenfield + research correction):
- RU header `// Phase 1 / REL-03: per-user deterministic percentage rollout via FNV-1a.`
- Export `Rollout(userID int64, flagName string, percent int) bool`:
  ```go
  if percent <= 0 { return false }
  if percent >= 100 { return true }
  h := fnv.New64a()
  binary.Write(h, binary.BigEndian, userID)
  h.Write([]byte{0x00})                   // SEPARATOR — research correction
  h.Write([]byte(flagName))
  bucket := int(h.Sum64() % 100)
  return bucket < percent
  ```
- The 0x00 separator byte is critical: without it, `(userID=1, flag="0foo")` and `(userID=10, flag="foo")` hash to the same input. Research-verified pitfall.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Mobile client → backend `GET /featureflags` | Untrusted user requests flag state; response shapes per-user rollout |
| Admin UI (`gateway/admin/index.html`) → backend `PUT /admin/featureflags/{name}` | Privileged write path; gated by permissions + audit |
| Postgres `featureflags` table → all services | Shared source of truth; cache lag is the only inconsistency window (30s) |
| MMKV storage → Zustand store | Persisted flag cache survives app kill; cleared on logout |
| FNV-1a `Rollout` decision boundary | Server makes the rollout decision for authenticated users; mobile mirror is advisory only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-C-01 | Spoofing | PUT /admin/featureflags/{name} | mitigate | `permissions.Check(subject, CapFeatureFlagToggle, ctx)` enforced via existing `pkg/permissions` admin role gate. The same gate protects existing admin endpoints (e.g., moderation) — re-uses the proven path. Non-admin users get 403. |
| T-01-C-02 | Tampering | Rollout predictability | mitigate | FNV-1a with 0x00 separator prevents boundary collisions (research correction). Per-user assignment is deterministic and tied to internal userID (not email or any value the user controls), so a user cannot manipulate their own rollout bucket. **NOT a security boundary** for high-stakes flags — `release_channel_force_update` and `strava_oauth_enabled` are operationally-staged, not adversarial. v1.1 may add HMAC-keyed rollout if a flag becomes security-relevant. |
| T-01-C-03 | Repudiation | Flag-flip audit trail | mitigate | Every `Set()` call writes `audit.LogQuiet` with capability `featureflag.toggle`, actor user_id, target flag name, and `{enabled, percent}` metadata. The audit log is queryable via existing admin UI Audit log section. Per OBS-04 (Phase 5) audit retention is configurable; for v1.0 it's permanent. |
| T-01-C-04 | Information disclosure | GET /featureflags response | mitigate | Public endpoint returns only resolved booleans (no rollout_percent, no description, no audit fields). The DTO is intentionally narrower than the admin DTO — see `flagResolvedDTO` vs `flagAdminDTO` in Task 2. A user cannot learn other users' flag states. |
| T-01-C-05 | Information disclosure | MMKV flag cache on device | accept | Flag names + booleans are not PII. An attacker with physical device access learns which v1.0 flags are enabled — same info that the running app surfaces via behavior. No marginal disclosure. |
| T-01-C-06 | Denial of service | Cache stampede on cache miss | mitigate | `singleflight.Group` coalesces concurrent fetches for the same flag key. Test 8 covers this. Stampede on different flag keys is bounded by `len(flags) <= ~20` for v1.0 — acceptable. |
| T-01-C-07 | Denial of service | Stale MMKV cache stuck on a kill-switched feature | mitigate | 5min TTL + per RESEARCH §Pitfalls #4 — refresh on app foreground (AppState change) + auth state change. The 5min worst-case lag for a kill switch is acceptable for v1.0 closed beta (`release_channel_force_update` is the most sensitive flag; 5min server-side propagation + 5min mobile TTL = 10min worst case, documented in ADR-0007 §3 Сценарии пересмотра). v1.1 may add NATS-broadcast invalidation. |
| T-01-C-08 | Elevation of privilege | clearAll wiring | mitigate | logout path is the authoritative reset point. If clearAll fails (e.g., dynamic import error), `console.warn` is captured but logout proceeds (per existing wallet clearAll pattern). Stale flag state after logout is preferable to a half-logout. |
| T-01-C-09 | Tampering | Admin UI CSRF | accept | Per CONCERNS.md §`/admin/` HTML dashboard, admin tokens are bearer JWT (not cookies). PUT requests carry `Authorization: Bearer` header which CSRF cannot forge cross-origin. The existing admin UI (reports + audit) shares this property — no new exposure. Phase 5 (OBS) may add CSP headers globally. |
| T-01-C-10 | Repudiation | Mobile-side flag overrides | mitigate | Mobile DOES NOT have a "force enable this flag" debug toggle in v1.0. All flags resolve via server response or bundled defaults. A user cannot enable a feature locally that the server has rolled-out at 0%. (Exception: `tester_debug_logging` per OBS-08 may have a Settings toggle in Phase 5 that bypasses server rollout for testers — that's intentional and audited per CRASH-04/OBS-08 design; documented but not implemented in this plan.) |
