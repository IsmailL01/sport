# ADR-0002: Гостевой режим

**Дата:** 2026-05-06
**Статус:** Accepted (deferred implementation)
**Контекст:** Round 3 P2 / спека §1 «Авторизация / онбординг»

## Контекст

Спецификация фитнес-приложения требует «гостевого режима с локальным хранением». CLAUDE.md проекта декларирует multi-tenant с дня 1 (`user_id` обязателен в схеме). Прямая поддержка sessions без `user_id` нарушит инвариант и потребует either nullable foreign keys или дублирующих anonymous-таблиц.

В Round 2 решено отложить implementation. Этот ADR фиксирует выбранную модель.

## Решение

Гостевой режим реализуется через **локальный anonymous user**, а не через nullable references.

### Контракт

1. На первом запуске, если пользователь нажимает «Попробовать без регистрации»:
   - Генерируется UUID v4 — это `localUser.id`.
   - В `useAuthStore` ставится `state: 'authenticated'` с user `{ id: 'guest-<uuid>', email: null, displayName: 'Гость', isGuest: true }`.
   - Токены — нет, `apiClient.getAccessToken()` возвращает null, sync-engine не пытается push.
2. Все сессии / records / wallet / etc — пишутся с этим `user_id` локально, как у обычного.
3. **Никакого сетевого взаимодействия**: feed-социальный, чаты, push не работают (graceful-disabled UI).
4. Опция «Привязать аккаунт»: пользователь вводит email + OTP, после успеха backend выдаёт реального user'а. SQLite-данные мигрируют: `UPDATE … SET user_id = ?` (батчем, atomic).
5. Если backend получает merge-конфликт (этот email уже зарегистрирован) — UI спрашивает, что делать: «продолжить со старым аккаунтом» (локальные данные guest'а отбрасываются с подтверждением) либо «отменить» (остаёмся гостем).

### Что НЕ делаем

- Не вводим nullable `user_id` в схеме БД. Все таблицы продолжают требовать `NOT NULL` `user_id`.
- Не делаем гостевые сессии backend-видимыми. Sync-engine при `isGuest=true` short-circuit'ит.
- Не пытаемся «починить» merge автоматически: пользователь явно подтверждает.

## Альтернативы

- **Nullable user_id**: ломает multi-tenant инварианты, делает все queries сложнее.
- **Anonymous user-row на сервере**: требует unconditional роутинга к серверу, что противоречит offline-first.
- **Не делать гостя**: соответствует ТЗ Running Ecosystem, но противоречит общему фитнес-спеку. Принят компромисс: гость = local-only, не «настоящий» multi-device аккаунт.

## Последствия

- Auth UI добавляет кнопку «Без регистрации». В Round 3 — UI-стаб только; реальная миграция guest→real откладывается до Round 4+.
- `useAuthStore.user.isGuest` boolean — новый флаг, гейтит social-features.
- Onboarding flow получает skip-on-guest path.
- Документация для пользователя — «Локальный режим: ваши данные хранятся только на этом устройстве, синхронизация и социальные функции отключены».

## Импликации для текущего раунда

В Round 3 написан только этот ADR. Фактической реализации `isGuest=true` flow в коде нет. UI кнопка «Без регистрации» в AuthStack не добавляется до отдельного раунда.

Это позволяет:
- Документировать решение, чтобы команда не пыталась импровизировать.
- Корректно отказать пользователю в P2 фиче с понятной причиной отсрочки.
